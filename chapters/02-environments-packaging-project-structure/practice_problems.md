# Chapter 2 — Practice Problems

Standalone exercises to drill packaging and environment concepts. Ordered easy to hard. No solutions provided.

1. **Create and inspect a venv** — Create a virtual environment with `venv`, activate it, install one package, then inspect where it was installed (`site-packages` path) versus your system Python's location.
   *Focus: understand exactly what isolation a venv provides.*

2. **`uv` vs `venv` speed test** — Create the same environment and install the same 5 packages once with plain `pip`/`venv` and once with `uv`; compare the time.
   *Hint: use `time` (Unix) or `Measure-Command` (PowerShell) around each flow.*

3. **Requirements file vs pyproject dependencies** — Take a `requirements.txt` with 3 packages and rewrite the same dependency set as a `[project.dependencies]` list in a minimal `pyproject.toml`.
   *Focus: notice what pyproject.toml gives you that a flat requirements file doesn't (metadata, build config).*

4. **SemVer reasoning** — Given a hypothetical dependency changelog (major/minor/patch bumps you invent), decide which version constraint (`==`, `>=`, `~=`, `<`) you'd use in a library vs an application, and justify each choice in a comment.
   *Focus: libraries want loose ranges; applications want locked exact versions.*

5. **Flat-to-src migration** — Take a flat-layout toy package (`mypkg/__init__.py` at repo root) and migrate it to `src/mypkg/__init__.py`, updating `pyproject.toml` package discovery so it still imports correctly after `pip install -e .`.
   *Hint: watch for accidental "it still works" false positives caused by the old flat import path lingering on `sys.path`.*

6. **Minimal pyproject.toml from scratch** — Write a `pyproject.toml` for a toy package by hand (not generated by a tool) with `[build-system]`, `[project]` metadata, and no dependencies; build it with `python -m build` and confirm a wheel is produced.
   *Focus: know the three PEPs' roles (517/518/621) as you fill in each section.*

7. **Add a console script entry point** — Add `[project.scripts]` to the toy package above so that after `pip install -e .`, running a new shell command prints something; verify it actually appears on your `PATH`.
   *Hint: reinstall after editing `pyproject.toml` — entry points aren't picked up by `-e` installs automatically without a reinstall in some tool versions.*

8. **TestPyPI publish dry run** — Build your toy package and (optionally) upload it to TestPyPI with `twine`, then `pip install` it from TestPyPI into a fresh venv to confirm the round trip works.
   *Focus: treat this as a rehearsal — use a throwaway package name.*

9. **`.env` + `pydantic-settings`** — Build a small `Settings` class using `pydantic-settings` that loads a required `database_url` and an optional `debug` flag from a `.env` file, and demonstrate what happens (a clear validation error, not a cryptic `KeyError` later) when a required value is missing.
   *Focus: fail fast and clearly at startup.*

10. **Secret leak detection** — Deliberately commit a fake secret to a throwaway git repo, then find and explain how you'd remove it from history (conceptually — tools like `git filter-repo`/BFG); write down why `.gitignore`-ing it *after* the commit isn't enough.
    *Hint: this previews Chapter 11 — the point here is understanding why git history is forever.*

11. **Multi-version compatibility check** — Using `pyenv` (or any means of getting two Python versions), install and run your toy package's tests (or just import it) under two different Python minor versions, and note any incompatibility.
    *Focus: `requires-python` should reflect versions you've actually verified, not versions you assume work.*

12. **Editable install vs real install divergence** — Deliberately create a bug that only manifests in a "real" (non-editable) install (e.g., forgetting to include a data file via package data config), reproduce it, then fix your `pyproject.toml` packaging config.
    *Focus: this is the exact class of bug the `src` layout and proper packaging config exist to catch early.*
