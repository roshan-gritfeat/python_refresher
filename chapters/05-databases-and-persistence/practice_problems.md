# Chapter 5 — Practice Problems

Standalone exercises, ordered easy to hard. No solutions provided.

1. **Raw sqlite3 basics.** Using only `sqlite3`, create a table, insert 5 rows with parameterized queries, and select them back.
   *Focus: use `?` placeholders, not string formatting, even though it's "just a script."*

2. **Transactions and rollback.** Write a script that starts a transaction, makes two related inserts, then deliberately raises an exception before committing; confirm neither insert persisted.
   *Hint: use the connection as a context manager, or explicit `.rollback()`, and check the table afterward in a fresh connection.*

3. **Write a join query.** Given `authors(id, name)` and `books(id, title, author_id)` tables, write a `LEFT JOIN` query that lists every author with their book count, including authors with zero books.
   *Focus: use `COUNT` with `GROUP BY`; a `LEFT JOIN` is required so zero-book authors aren't dropped.*

4. **Index impact.** On a table with 100k+ rows, run the same `WHERE` query with and without an index on the filtered column, using `EXPLAIN QUERY PLAN`, and compare.
   *Hint: SQLite's `EXPLAIN QUERY PLAN` will literally say "SCAN" vs "SEARCH" — look for that difference.*

5. **Define SQLAlchemy models.** Model a `Customer` and `Order` (one-to-many) using SQLAlchemy's declarative ORM with type-annotated `Mapped` columns and a `relationship()`.
   *Focus: get the `ForeignKey` and `relationship()` direction right — Order references Customer, Customer has a collection of Orders.*

6. **CRUD via SQLAlchemy ORM.** Using the models from problem 5, write functions to create, read, update, and delete an `Order`, using a `Session`.
   *Hint: remember to `session.commit()`; forgetting it is the SQLAlchemy equivalent of forgetting `conn.commit()`.*

7. **Write and apply an Alembic migration.** Set up Alembic for the models in problem 5, generate an initial migration, then add a new nullable `status` column to `Order` via a second migration.
   *Focus: review the autogenerated migration file before applying it — don't just trust it blindly.*

8. **Reproduce an N+1 query.** Fetch 20 customers and print each one's order count by accessing `customer.orders` in a loop with lazy loading; count the number of SQL statements executed (e.g., via SQLAlchemy's echo=True).
   *Hint: turn on `echo=True` on the engine and literally count the SELECT statements printed.*

9. **Fix the N+1 with eager loading.** Rewrite problem 8's query using `joinedload` or `selectinload` and confirm (via the same echo output) that the number of queries drops to 1 or 2.
   *Focus: compare query counts before/after explicitly — that comparison is the point of the exercise.*

10. **Downgrade a migration.** Using the migrations from problem 7, run `alembic downgrade -1` and confirm the `status` column is actually removed from the schema.
    *Hint: inspect the schema directly (e.g., `.schema orders` in the sqlite3 CLI) rather than trusting Alembic's own output.*

11. **Build a cache-aside function.** Write a `get_or_compute(key, compute_fn, ttl)` helper backed by Redis (or `fakeredis` for testing) implementing the cache-aside pattern, with a test proving `compute_fn` is only called once across repeated calls within the TTL.
    *Focus: assert the call count of a mock `compute_fn` stays at 1 across multiple `get_or_compute` calls.*

12. **Cache invalidation on write.** Extend problem 11 into a small "product price" service where updating a price explicitly deletes the corresponding cache key, and write a test proving a stale cached value is never returned after an update.
    *Hint: the test should fail if you forget to call the cache-delete on the update path — write the test first (TDD) to confirm that.*
